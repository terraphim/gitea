# Research Document: Cherry-pick 4 Missing Upstream Security Commits

**Finding: all four "missing" commits are already on `main`.** The issue body
appears to have been generated by an upstream-drift check that searched for
upstream SHAs in fork history; because each pick was re-applied with a fresh
SHA (with `cherry picked from <upstream>` trailers in three of four cases, and
a manual surgical adaptation in the fourth), the upstream SHA search produced

## Problem Statement

### Description

Issue #34 claims the fork is missing four upstream security commits:

1. `f3bdcc58af` -- Fix OAuth2 authorization code expiry and reuse handling (#36797)
2. `6ed861589a` -- Fix container auth for public instance (#37290)
3. `63db5972a1` -- fix(oauth): Error on auth sources with spaces (#37327)
4. `6826321570` -- feat(security): set X-Content-Type-Options: nosniff by default (#37354)

### Verification Method

For each upstream SHA, the verifier:

1. Searched `git log main --grep="<upstream PR number>"` for the same PR ref.
2. Compared `git show <upstream-sha> -- <files>` to `git show <fork-sha> -- <files>`.
3. Inspected commit-trailer for `cherry picked from`.

## Why the Issue Was Opened Anyway

The `upstream-synchronizer` agent likely:

- Compared upstream SHAs to fork SHAs directly via `git branch --contains` or
  `git log --grep=<upstream-sha>`. Re-applied commits have different SHAs and
  do not appear via that lookup.
- Did not parse `cherry picked from <upstream-sha>` trailers in commit messages.
- Did not parse `Adapted-from: <upstream-sha>` trailers used for surgical picks.

This is a false-positive class. Recommendation: enrich the drift detector to
scan trailers and PR-number references rather than only SHA presence.
